# p2p · 事件流 + 认领 + 担保

> 没有中心，怎么判断"这条标注可信"？答案不是手机号，是密码学。

## 为什么不用手机号

| 手机号的假设 | 现实 |
|---|---|
| 一个号 = 一个人 | 一家三口共用一号；一个老板开两家店 |
| 认证 = 可信 | 手机号只能证明"号是活的"，不能证明"店是你的" |
| 能挡住刷子 | 接码平台几毛钱一个号，挡不住有组织的，只挡住普通人 |
| 技术可行 | 个人主体申请不了短信签名，微信 `getPhoneNumber` 也不对个人开放 |

**根本矛盾**：短信验证必须有一个中心发码、校验；而 P2P 架构定义上就没有中心。
就算硬塞一个，A 手机告诉 B 手机"这条已验证"，B 凭什么信？**"已验证"这个状态本身需要权威签发。**

## 三层信任

```
① 密码学签名     每条事件带作者签名，离线可验，改不了别人的
② 认领 + 担保    店主用私钥认领，需要 2 位已认领店主作保
③ 时间与多数     结构性字段按独立作者数投票；时效性字段按最新观测，7 天失效
```

## 认领为什么不是"先到先得"

最早的版本是"谁先认领谁就算店主"——**这是个大窟窿**：冒名者抢在真店主之前点一下，店就归他了。

改成**担保优先**：

| 谁作保 | 需要几位 |
|---|---|
| 发起人（根信任，内置公钥） | 1 位 |
| 其他已认领的店主 | 2 位 |
| 没人作保 | 不给 L2，只显示"待担保" |

冒名者拿不到任何担保签名，**抢多早都没用**。而担保人本身必须已经可信，
所以信任是沿着熟人网络长出来的——这正好是县城商圈的真实结构。

担保签名自带公钥（自证明），任何设备拿到就能验，**不需要事先认识担保人，也不需要中心登记**。

## 四类事件

| 类型 | 含义 | 谁可以发 |
|---|---|---|
| `anchor` | 这儿有家店（名称/坐标/地址） | 任何人（冷启动必需） |
| `claim` | 这家店归我管，附担保人签名 | 任何人（担保够才算数） |
| `fact` | 今天开着 / 有什么货 / 运力 | 任何人，带有效期 |
| `deny` | 这条不是我说的，作废 | **只有店主**，且只能指向自己的店 |

## 归约规则

1. 验签失败、被店主 `deny` 的，直接丢弃
2. **认领全局解析**：担保链可跨店传播（老陈给自己店认领后，就能替张姐作保）
3. **结构性字段**（店名/地址/电话/坐标）：店主优先；无主时按**独立作者数投票**，平票取最早
4. **时效性字段**（营业/货品/备注）：店主优先；无主时取**最新观测**；超过 7 天失效
5. **不裁决分歧**：矛盾值全部呈现，只统计人数

投票按**人数**不按**条数**——一台设备刷一百条也只算一票。

## 跑起来

```bash
python p2p/identity.py     # 签名层 8 项自检
python p2p/selftest.py     # 认领+担保 29 项自检
python p2p/demo.py         # 五台手机碰面，看同一条街
```

## 还剩的风险（诚实清单）

| 问题 | 严重度 | 现状 |
|---|---|---|
| ~~认领先到先得~~ | ~~🔴~~ | ✅ **已被担保机制解决** |
| **根密钥泄露**：发起人私钥被盗，可任意担保 | 🔴 高 | 根私钥应离线冷存；正式版考虑多根（M-of-N） |
| **担保人串通**：两位店主合谋给冒名者作保 | 🟠 中 | 串通损害自身声誉；可加"7 天争议期" |
| **无根的首次部署**：走 bootstrap，最早认领直接生效 | 🟠 中 | 只影响第一个部署点；建议种子包预置根公钥 |
| 时钟可被篡改：排序依赖设备本地时间 | 🟠 中 | 正式版换 Lamport / 混合逻辑时钟 |
| 事件永久保存，永不删除 | 🟠 中 | 电话等敏感字段旧版本一直留着，需本地裁剪策略 |
| RSA 1024 教科书式签名 | 🟡 低 | **原型专用**，正式版换 Ed25519 |

## 与前面几版的关系

| 方案 | 状态 |
|---|---|
| 本地服务 + 局域网（`server.py`） | ✅ 可用，同 WiFi 兜底 |
| 微信云开发（`cloud/`） | ✅ 可用，远程可见 |
| 事件流 + 认领 + 担保（`p2p/`） | ✅ 地基已通，等一个载体（Android App） |

三套不冲突：**认领产生的可信度，任何载体都能用。**
