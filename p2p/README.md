# p2p · 事件流 + 认领机制

> 没有中心，怎么判断"这条标注可信"？答案是密码学，不是手机号。

## 为什么不用手机号

| 手机号的假设 | 现实 |
|---|---|
| 一个号 = 一个人 | 一家三口共用一号；一个老板开两家店 |
| 认证 = 可信 | 手机号只能证明"号是活的"，不能证明"店是你的" |
| 能挡住刷子 | 接码平台几毛钱一个号，挡不住有组织的，只挡住普通人 |
| 技术可行 | 个人主体申请不了短信签名，微信 `getPhoneNumber` 也不对个人开放 |

**根本矛盾**：短信验证必须有一个中心发码、校验；而 P2P 架构定义上就没有中心。
就算硬塞一个，A 手机告诉 B 手机"这条已验证"，B 凭什么信？**"已验证"这个状态本身需要权威签发。**

## 换成"认领"

```
路人：这儿有家店              →  L0，30 天没人认领就淡出
多人：三个人都说这家开着      →  L1，参考级
店主：用自己的私钥签名认领    →  L2，从此他说了算
```

认领不需要短信、不需要网络、不需要花钱——**一对密钥就是所有权凭证**。
别人拿到公钥，离线就能验证"这条标注确实出自那把私钥"。

## 四类事件

| 类型 | 含义 | 谁可以发 |
|---|---|---|
| `anchor` | 这儿有家店（名称/坐标/地址） | 任何人（冷启动必需） |
| `claim` | 这家店归我管 | 任何人（先到先得，后来者记为争议） |
| `fact` | 今天开着 / 有什么货 / 运力 | 任何人，带有效期 |
| `deny` | 这条不是我说的，作废 | **只有店主**，且只能指向自己的店 |

## 归约规则（把乱序事件算成"此刻的街"）

1. 验签失败、被店主 `deny` 的，直接丢弃
2. **认领权先到先得**，后来的 claim 记为 `contested`（争议），供人查看
3. **结构性字段**（店名/地址/电话/坐标）：店主优先；无主时按**独立作者数投票**，
   平票取最早——**一个人改不掉别人已经标好的店名**
4. **时效性字段**（营业状态/货品/备注）：店主优先；无主时取**最新一次观测**；
   超过 7 天自动失效
5. **不裁决分歧**：同一字段出现矛盾，统计各方人数并全部呈现，不做"谁对"的判断

## 跑起来

```bash
python p2p/identity.py     # 签名层 8 项自检
python p2p/selftest.py     # 认领机制 22 项自检
python p2p/demo.py         # 三台手机碰一面，看同一条街
```

## 已知窟窿（不要假装没有）

| 问题 | 严重度 | 缓解办法 |
|---|---|---|
| **认领先到先得**：冒名者抢先认领，真店主就丢了 | 🔴 高 | 认领时要求物理在场（扫店内码 / 同 WiFi）；或设 7 天争议期；或种子包预置真店主公钥 |
| 时钟可被篡改：排序依赖设备本地时间 | 🟠 中 | 正式版换 Lamport/混合逻辑时钟，不信任墙壁时间 |
| 事件永久保存，永不删除 | 🟠 中 | 电话等敏感字段的旧版本会一直留着，需要"本地裁剪"策略 |
| 一人可造多把密钥刷 L1 | 🟡 低 | L1 只是参考级，L2 店主一票否决；刷 L1 收益极低 |
| 首次同步是全量事件 | 🟡 低 | 事件多了要加快照压缩，否则新设备同步慢 |
| RSA 1024 教科书式签名 | 🟡 低 | **原型专用**，正式版换 Ed25519，体积小速度快、无填充陷阱 |

## 与前面几版的关系

| 方案 | 状态 |
|---|---|
| 本地服务 + 局域网（`server.py`） | ✅ 可用，同 WiFi 场景兜底 |
| 微信云开发（`cloud/`） | ✅ 可用，远程可见 |
| 事件流 + 认领（`p2p/`） | ✅ 地基已通，等一个载体（Android App） |

三套不冲突：**认领产生的可信度，任何载体都能用**。
